# Track — guidance for Claude Code

Track is a private family PWA for logging a child's day. These are the sources of truth, in order:

1. `docs/requirements.md`: functional, non-functional and technical requirements. Follow section 7 (stack, architecture, data model, API) exactly. If something proves unworkable, stop and raise it with the repository owner. Don't quietly change the approach.
2. The existing UI (`src/client`, design tokens in `src/client/styles/tokens.css`): layout, components, colours, typography, light and dark themes. Match it. Where it conflicts with the requirements' accessibility rules, the requirements win.
3. `docs/implementation-plan.md`: how it was built and the decisions behind it.

Each family deploys its own private copy. Per-deployment values (domains, Access team and AUD tags, D1 IDs) live only in `wrangler.jsonc` and GitHub secrets and variables (see the README). Never commit real people's names, emails or children's data to this repository: tests use the fictional family in `scripts/fixtures.ts` (Alex, Jamie and Sam).

## Stack (TECH-01, fixed)

TypeScript everywhere · React + Vite (PWA) · one Cloudflare Worker with static assets · Hono for `/api` · Zod schemas shared by the frontend and the API · Cloudflare D1 · Drizzle ORM, with migrations applied by Wrangler · Lucide icons · Vitest · Playwright (Pixel 7 and Pixel 6a).

## Layout

```
src/
  shared/     pure TS shared by the client and the Worker: zod schemas, schedule, matching, medication, time, csv
  worker/     Hono app, auth middleware, routes, db (drizzle schema)
  client/     React app: tokens.css, components/, screens/, sync/, sw/
migrations/   Wrangler D1 migrations (SQL, generated by drizzle-kit and checked in)
scripts/      seed generator, test fixture and demo data, first-Admin SQL, screenshots, helper scripts
test/         Vitest: shared/, client/, node/ (Node) and worker/ (Workers runtime and D1); fixtures/
e2e/          Playwright tests
.github/workflows/  ci.yml, deploy-production.yml, deploy-preview.yml, refresh-preview.yml
```

## Commands

These are the checks to run locally before any push. `npm run check` runs all of them except e2e.

- `npm ci`: install. The lockfile was made with npm 11, which blocks install scripts unless allowed (`allowScripts` in package.json). CI uses Node 24, whose npm 11 matches the lockfile.
- First local run: `cp .dev.vars.example .dev.vars && npm run db:migrate:local`, then either `npm run seed:demo` (fictional demo family) or `npm run db:admin:local` (just you as Admin, from `DEV_AUTH_EMAIL`)
- `npm run dev`: Vite and the Worker locally (`wrangler dev`, local D1, dev auth stub)
- `npm run db:migrate:local`: apply migrations to the local D1
- `npm run db:generate`: drizzle-kit, generate a new migration from `src/worker/db/schema.ts`
- `npm run seed:generate`: regenerate the seed migration from `scripts/seed-data.ts` and the test fixture from `scripts/fixtures.ts` (`npm run seed:check` checks they're in sync, as does `npm test`)
- `npm run screenshots`: regenerate `docs/screenshots/` from the demo data
- `npm run typecheck` · `npm run lint` · `npm run format:check`
- `npm test`: Vitest, unit and Worker tests
- `npm run e2e`: Playwright at Pixel 7 and Pixel 6a with axe, against a fresh local D1 with the test family (`npm run e2e:server`). To use a Chromium that's already installed, set `PW_CHROMIUM_PATH` (for example `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium npm run e2e`). Tests must create and clean up their own data, because both device projects share one database.
- `npm run build`: client build and Worker bundle check (`wrangler deploy --dry-run`)

Before every push, run typecheck, lint, test and build. Before pushing a UI change, also run the e2e tests.

## Hard rules

- **Never touch production yourself.** No `wrangler d1 execute/migrations apply/export` and no `wrangler deploy` against `track-prod`, `track-preview`, `--remote`, `--env production` or `--env preview`. Only GitHub Actions touch deployed data: changes reach production only when the repository owner merges a PR to `main`, which runs the deploy workflow. Local commands always use `--local`.
- Don't change Cloudflare Access, and don't use Workers Builds (Cloudflare Git integration). GitHub Actions deploys everything.
- **Auth (TECH-05).** Every `/api` request verifies `Cf-Access-Jwt-Assertion` against `https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs` and the environment's `ACCESS_AUD`. Never trust `Cf-Access-Authenticated-User-Email` on its own. Then look up the user (lowercased email, must be active), then run role middleware on every route (R / W / A, per section 7.11).
- **Dev auth stub** (local and Playwright only):
  - It turns on only when `DEV_AUTH_STUB=1` is set from `.dev.vars` (gitignored) or a local `--var`.
  - It also requires _no_ `ACCESS_AUD` or `ACCESS_TEAM_DOMAIN` to be configured, and the request hostname to be `localhost` or `127.0.0.1`.
  - Production and preview always set both Access vars in `wrangler.jsonc` (a unit test checks this), so the stub can't run there. If the flag is set alongside Access config, every `/api` request fails with 500 (fail closed). A unit test covers this. Never weaken any of these checks.
- No third-party scripts, fonts, analytics or CDNs (NFR-06). Fonts (DM Sans) and icons are bundled. Keep the CSP strict: `default-src 'self'`, no `unsafe-inline` scripts.
- Only `/manifest.webmanifest` and `/icons/*` bypass Access. Keep those paths exactly.
- Entry IDs are ULIDs made on the client. `PUT /api/entries/:id` is idempotent.
- Every write bumps `sync_state.version` **in the same D1 batch**.
- Migrations: create tables in dependency order (parents first) and never edit a migration that has been merged. Worker tests (`test/worker`) run in workerd against a real local D1 with every migration applied, plus the fictional test family.
- Keep D1 work batched: at most 50 queries per invocation, at most 100 bound parameters per query (TECH-14). Bootstrap, backup and import use `db.batch`.
- Store times as `start_utc` / `end_utc` (ISO UTC), plus `tz` (IANA) and `local_date`. Schedule times are plain `HH:MM`, applied in the phone's current time zone. Use `Intl` only, never hard-coded offsets.
- Medication, matching, missed items and planned-item generation live in `src/shared`, are pure (pass `now` and `tz` in) and are unit-tested. The UI never re-implements them.
- The app gives no medical advice. All doses, gaps and limits come from Settings.

## UI conventions

- Design tokens are CSS variables in `src/client/styles/tokens.css`, under `:root` (light) and `[data-theme="dark"]`. The theme choice (System, Light or Dark) is stored in `localStorage` per device. System follows `prefers-color-scheme` live.
- Activity colours are the palette tokens `amber orange blue green violet red brown teal indigo slate pink`, each with `fg` and `bg` per theme. Never accept arbitrary colours or icons.
- Accessibility is WCAG 2.2 AA in both themes:
  - Interactive targets are at least 44×44 CSS px.
  - Every activity shows a text label, never only an icon or a colour.
  - Real `<button>`, `<a>`, `<input>` and `<label>` elements.
  - `aria-label` on icon-only buttons; decorative SVGs get `aria-hidden`.
  - Focus is always visible.
  - Text contrast is at least 4.5:1, and UI component boundaries at least 3:1.
- UK English in all copy. Times use the 24-hour clock (`HH:MM`). Dates are `dd/mm/yyyy` or "Sat 18 Oct". Weeks start on Monday. Units are metric.
- Read only users never see logging or editing controls. Offline, those controls are disabled.

## Git and PRs

- One branch and one PR per change. When deploys are switched on, each PR deploys to the preview address for the owner to test.
- Commit messages are imperative and describe the change. Don't push to `main`.
- Never put secrets, account tokens or model identifiers in commits.
